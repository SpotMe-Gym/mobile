# SpotMe Mobile — Folder Structure

> How the code is organised and where new code goes.
> Enforced by tooling: `@/` → `src/` (`tsconfig.json`), and ESLint blocks `src/shared` from importing features.

## Why it changed

The old layout split each feature across five technical folders. The nutrition feature, for example, lived in `components/food/`, `components/nutrition/`, `hooks/useFood.ts`, `services/foodApi.ts`, `store/nutritionStore.ts` and `utils/portion.ts`. Three folders (`lib/`, `utils/`, `services/`) had overlapping meanings, and imports mixed `@/…`, `./…` and `../../../…`.

The new layout is **feature-first**:
- Everything about one product area lives in one folder.
- Anything reused across areas lives in `shared/`.
- Every import uses `@/`.

## Dependency rules

```
app/  ──►  features/  ──►  shared/  ──►  theme/
  │            │  ▲            ▲
  └────────────┼──┘            │
               └─ other features (sparingly)
```

| From | May import | Must not import |
|---|---|---|
| `src/app/*` (routes) | features, shared, i18n, theme | — |
| `src/features/<x>` | shared, i18n, theme, **another feature's store/hooks/utils** when it genuinely needs that data | `src/app` |
| `src/shared/*` | shared, theme | features, app *(ESLint error)* |
| `src/i18n` | the profile store (for the saved language) | anything else |

Cross-feature imports that exist today, all intentional:
- `useUnitConverter` (profile) reads the latest weight from body-weight.
- The dashboard widgets render cards from nutrition, body-weight and workouts.
- Onboarding uses the target calculator from nutrition and the weight store from body-weight.

## Where does new code go?

| You're adding… | Put it in |
|---|---|
| A new screen / URL | `src/app/<route>.tsx`. Keep it thin and compose feature components. |
| A component used by one feature | `src/features/<feature>/components/` |
| A reusable primitive (button, input, chip…) | `src/shared/ui/` |
| A hook for one feature (incl. TanStack Query) | `src/features/<feature>/hooks/` |
| A hook any feature could use | `src/shared/hooks/` |
| A network client | `src/features/<feature>/api/` (generic fetch helpers: `src/shared/lib/http.ts`) |
| Pure logic / maths | `src/features/<feature>/utils/`, or `src/shared/utils/` if not feature-specific |
| A Zustand store | `src/features/<feature>/<name>Store.ts`, exporting its `migrate…State` function |
| A zod schema | `src/features/<feature>/schemas/` or `<name>Schema.ts` at the feature root |
| A new home-screen widget | `src/features/dashboard/widgets/<name>.tsx`, then register it in `widgets/catalog.ts` |
| A new product area | `src/features/<area>/` with the same sub-folders (create only the ones you need) |
| Translations | `src/i18n/locales/en.json` **and** `it.json` (CI checks parity) |
| Colours | `src/theme/colors.ts` only |

## Conventions

- **Imports:** always `@/…`, never relative, even for siblings. One style everywhere, and moving a file never breaks its neighbours' imports.
- **Naming:** folders `kebab-case`, components `PascalCase.tsx`, hooks `useThing.ts`, stores `thingStore.ts`, schemas `thingSchema.ts`, everything else `camelCase.ts`.
- **Tests:** next to the code they test (`portion.ts` + `portion.test.ts`). Never inside `src/app/`: every file there becomes a route.
- **No barrel files** except `features/dashboard/widgets/index.ts`, which collects widget definitions for the catalog.
